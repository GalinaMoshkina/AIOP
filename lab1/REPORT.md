## Выделенные конвенции

Из конвенций мы выделили следующие:  
1. **Ports & Adapters:** Код не просто разделён на папки, есть конкретное правило: ядро (`/src/lib/bounded-contexts`) работает через порты, а остальные части проекта (`infrastructure`) предоставляют адаптеры (`/src/api`) для общения с ним.
2. **CQRS (Command Query Responsibility Segregation):** В проекте есть разделение на `commands` (которые выполняют операции записи, удаления и тд) и `queries` (которые только читают данные).
3. **BDD (Behavior-Driven Development):** Тестируются не только отдельные классы, а поведение через `command`/`query handlers`. При этом реальные БД и адаптеры заменяются mock-реализациями. Проверяется `use-case`, а не отдельное поведение БД и тд.
4. **Разделение Domain и Application errors:** В проекте `domain layer` содержит Domain Errors, а `application layer` имеет собственные `application errors`. При создании `errors` надо сначала определить, к чему она относится.
5. **Версионирование контрактов:** Для связи bounded contexts используются integration events как публичные контракты. Если контракт `integration event` меняется (и версия становится несовместимой), должна появиться новая версия, чтобы не ломать `consumers` старой версии (т.е. условно: `UserRegisteredV1; UserRegisteredV2`, а не просто изменение существующего `UserRegistered`). Старая версия поддерживается, пока `consumers` не перестают ее читать.
6. **Event Sourcing + Transactional Outbox:** Состояние агрегата хранится как append-only поток событий. Todo восстанавливается проигрыванием (`replay`) этих событий. `Events`, `projection` и `outbox` записываются в одной PostgreSQL transaction. `Outbox relay` затем публикует события в `NATS` с повторными отправками и `at-least-once delivery`.
7. **DTO на внешних границах:** Контроллеры работают с DTO, а доменная модель не должна превращаться в `HTTP response` напрямую. В проекте DTO находятся в `presentation/API layer`, а `domain objects` находятся внутри `domain layer`.

Агент в целом реализовал требуемую функциональность: добавил `page`, `limit`, `status`, изменил формат ответа на items/total/page/limit, добавил проверки входных параметров и тесты controller.

Однако при сравнении с конвенциями проекта видны следующие проблемы:

1. DTO на внешних границах: `GetAllTodosResponseDto` напрямую зависит от `TodoReadModel` из domain, а controller также импортирует domain read model и сначала преобразует данные в TodoReadModel, после чего передаёт его в DTO. То есть API layer знает о domain model, хотя DTO должны быть независимым внешним контрактом.
  
2. Ports & Adapters: новая логика в основном идёт через query и read repository port, но в DTO добавлена логика валидации через `BadRequestException` из NestJS. Это не является прямым нарушением core/application boundaries само по себе, поскольку DTO находится в API layer, однако показывает смешение транспортной логики с преобразованием данных. Более существенная проблема сохраняется в application layer проекта: `GetTodosHandler` использует @Inject из NestJS, то есть application code зависит от framework. Это противоречит правилу, которое утверждает, что application layer не должен содержать framework infrastructure code.
   
3. BDD / use-case tests: добавлены controller-level tests, которые проверяют HTTP endpoint и mock queryBus, но полноценного теста самого `GetTodosHandler` с mock `TodoReadRepoPort` для нового поведения нет. То есть тестируется API boundary, но не полностью use case через application layer.
   
4. Избыточная логика в API: парсинг `page`, `limit` и `status` реализован непосредственно внутри DTO-файла (`parseTodoListQuery`). В результате DTO становится не только описанием внешнего контракта, но и содержит довольно много процедурной валидации. При этом в проекте уже есть отдельный механизм DTO/validation, поэтому решение получилось более ручным, чем необходимо.

Сделаем ещё один прогон на отдельной ветке репозитория — на `baseline-attempt-2`. Используем тот же промпт на изначальном состоянии проекта.

Заметно, что теперь пропущенных тестов стало меньше, но их всё ещё больше, чем на основном прогоне.  

Во второй попытке агент сделал решение более структурированным. Появился отдельный `GetAllTodosRequestDto` с class-validator, `ValidationPipe`, интеграционный тест PostgreSQL и отдельные controller tests. То есть часть проблем первой попытки была исправлена.

Но основные архитектурные проблемы остались:

1. DTO всё ещё зависит от domain: `GetAllTodosRequestDto` и `GetAllTodosResponseDto` находятся в API layer, но `get-all-todos.dto.ts` импортирует `TodoReadModel` из domain. Более того, controller продолжает импортировать `TodoReadModel` и создавать его из результатов query перед передачей в response DTO. Таким образом, основное нарушение DTO boundary из первой попытки осталось.
   
2. Application layer всё ещё зависит от NestJS: `GetTodosHandler` содержит import { Inject } from '@nestjs/common'. Следовательно, application handler по-прежнему связан с NestJS, несмотря на правило Ports & Adapters о независимости application/domain от инфраструктуры и framework.
   
3. BDD / use-case testing: ситуация стала лучше, потому что появились mock repository и существующие feature tests были адаптированы под новый результат. Однако новые тесты в основном проверяют controller и infrastructure repository. Отдельного application-level теста `GetTodosHandler` с mock port, который проверяет новое поведение page/limit/status, не появилось.

4. Есть дублирование ответственности за валидацию: часть валидации находится в DTO через `class-validator`, а транспорт дополнительно настраивает `ValidationPipe`. Само использование `ValidationPipe` нормально, но решение получилось довольно сильно завязано на NestJS прямо в controller, что дополнительно подчёркивает общую проблему зависимости application/core от framework.

Заметим, что всего нарушений за каждую попытку:
1. `baseline-attempt-1`: 8 шт.
2. `baseline-attempt-2`: 3 шт.

То есть во второй раз стало меньше ошибок, которые бы поймали тесты. Однако обе попытки повторяют одни и те же архитектурные ошибки, несмотря на разные способы реализации.

## Проверка генерализуемости

Теперь проверим, как отработает агент с указаниями на другой задаче: попробуем дать попросить его реализовать soft delete для сущности Todo вместо физического удаления. Составим промпт, и прогоним тесты.  

```
Реализуй soft delete для сущности Todo вместо физического удаления. Запись помечается как удалённая, исключается из обычных списков, но остаётся в базе.
- DELETE /todos/:id — мягкое удаление, возвращает 204
- POST /todos/:id/restore — восстановление, возвращает 200 с телом задачи
- GET /todos — исключает мягко удалённые записи из результата
- Оба эндпоинта проверяют принадлежность задачи текущему пользователю
- Задача не найдена или уже в нужном состоянии: 404
- Поле deletedAt (nullable timestamp) в агрегате Todo
- Метод markAsDeleted() — устанавливает deletedAt = now, генерирует событие TodoSoftDeleted
- Метод restore() — сбрасывает deletedAt в null, генерирует событие TodoRestored
- Инварианты: нельзя удалить уже удалённую, нельзя восстановить не удалённую
- События TodoSoftDeleted и TodoRestored публикуются в шину событий
- Projection обновляет read-model при получении этих событий
```

*сюда скрин*  

Чисто в теории агент хорошо справился с задачей, реализовав soft delete и восстановление Todo с учётом основных архитектурных подходов проекта. Для проверки результата попросим LLM проверить изменения на соответствие конвенциям, которые были выявлены ранее, но затем обязательно проверим замечания вручную, так как модель может пропустить реальные нарушения.

Замечания к соблюдению конвенций следующие:

1. BDD / use-case tests: основная функциональность реализована через `Command` и `Handler`, однако тесты в коммите в основном проверяют непосредственно `TodoEntity` (`markAsDeleted()`, `restore()`, восстановление из истории). При этом отсутствуют полноценные application-level тесты через `DeleteTodoHandler` и `RestoreTodoHandler` с mock-реализациями портов. То есть тестируется отдельная domain-логика, но не весь use case через application layer, как требует конвенция BDD.
   
2. DTO на внешних границах: новый `restore endpoint` напрямую возвращает `TodoReadModel`, который находится в `domain layer`. В результате controller знает о domain read model и фактически использует её как HTTP response. Это нарушает правило разделения внешнего API и domain layer: controller должен возвращать отдельный DTO и преобразовывать в него данные read model.
   
3. Domain и Application errors: в целом разделение ошибок между слоями сохранено, однако в `DeleteTodoHandler` и `RestoreTodoHandler` domain errors преобразуются в `TodoNotFoundError`. Например, попытка восстановить Todo, который уже не удалён, приводит к `TodoNotFoundError`, хотя Todo фактически существует. Аналогично, попытка повторно удалить уже удалённый Todo трактуется как отсутствие Todo. Таким образом, теряется исходная причина domain-ошибки.
   
4. Ports & Adapters: новая функциональность в основном проходит через существующие ports, а работа с persistence остаётся в infrastructure adapter. Однако в новом `TodoWriteRepoPort` используется тип `Either`, который в файле не импортирован. Это может привести к ошибке type checking и должно быть проверено отдельно. (Так и есть, из-за этой ошибки код не компилируется, но я бы не сказала, что это из-за плохих инструкций, а скорее по невнимательности агента).
   
5. Event Sourcing + Transactional Outbox: soft delete и restore реализованы через новые domain events (`TodoSoftDeletedDomainEvent` и `TodoRestoredDomainEvent`), а события сохраняются вместе с outbox-записями в рамках транзакции. То есть основная конвенция соблюдена. При этом необходимо отдельно проверить цепочку публикации integration events, поскольку новые domain event handlers также вызывают eventBus.publish(), и важно убедиться, что это не создаёт обход или дублирование предусмотренного механизма Transactional Outbox.

Посмотрев на эти части кода самостоятельно, мы можем подтвердить, что основные замечания действительно присутствуют в коммите. В остальном структура soft delete соответствует существующей архитектуре проекта: используется CQRS, изменения проходят через domain events, сохраняется Event Sourcing, а integration events версионируются. Поэтому в целом агент с задачей справился относительно неплохо, но тесты use case, DTO boundary и обработку domain errors необходимо было реализовать точнее.
